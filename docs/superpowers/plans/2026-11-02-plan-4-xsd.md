# Plan 4 — XSDs: the published set read, blueprints, self-contained generation, and the drift report

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- Read the published `/api/v1/` XSD set once, and learn from it the business objects (blueprints) that many messages
  carry.
- Bind every module's elements to those blueprints, and resolve the conditions' entity-name paths through them.
- Generate one self-contained XSD per message and version.
- Prove the generator against the two published sets that match a workbook exactly.

**Architecture:**
- **`spec-model`**, pure as before:
  - code-list key types;
  - blueprint matching, binding and the consistency check;
  - the entity-name route in the condition binder;
  - the **schema shape**: one tree form that both a generated and a published XSD reduce to;
  - the generator: model → shape → XSD text;
  - the comparison of two shapes, and the drift report's causes;
  - synthetic messages.
- **The importer** gains an XSD reader on `saxes` that turns a published message into the same shape. It also learns
  the blueprint catalogue from the set, and passes the catalogue to the module import.
- **Tests** use libxml2's `xmllint`, compiled to WebAssembly, as the real validator.

**Tech Stack:** Node 24, CommonJS, `node --test`.
- `saxes` 5.0.1: already installed, as exceljs' parser, and now a direct dependency of the importer.
- `xmllint-wasm` 5.3.0: a dev dependency of the importer, approved by Boris on 2026-11-02. MIT, no dependencies,
  published 2026-08-05.

## Decisions this plan takes

Boris settled 1–4 on 2026-11-02 (recorded in §2 and §4.10). The rest are this plan's own, measured on 2026-11-02 and
recorded in the design record. Reject any of them at review, before Task 1.

1. **Self-contained XSDs.** One file per message: no `xs:include`, no `xs:extension`, no `xs:choice`, no shared
   types. The only import is xmldsig.
2. **The wire is unchanged:** tags, attributes, their order, and the namespace `https://www.his.bg`.
3. **Code lists are typed by key type,** never enumerated.
4. **Blueprints are internal.** `SPEC_KIND.COMMON_SCHEMA` goes.
5. **Blueprints fold by derivation only.** On the published set, `NHIS-Entities`' 24 types make 18 blueprints, and five
   message-local types fold in. Folding by name stem adds nothing on this set.
6. **A name matches a blueprint by a run of words.** Case is ignored, and a camel-cased name is split into words:
   Practitioner matches `medicalPractitionerSimple`, Diagnosis `diagnosisBasic`, `'diagnosticReport'` the type
   `diagnosticReport`. Look-alikes are folded by the importer before matching, since `spec-model` has no script
   tables. A name two blueprints match is matched by neither.
7. **A workbook name no blueprint matches is not reported.** That is 77 rows, among them Referral, Examination and Sick
   Leave. What is reported is a name that contradicts the type or sibling binding of its element, and none does today.
   This amends §4.4 as first approved.
8. **The catalogue is one frozen, JSON-safe value.** `importXsdSet` produces it, and `importSet` and
   `importModuleWorkbook` take it as an option. Storing it is plan 5's. Without it, nothing is bound, and every result
   of plans 1–3 is unchanged.
9. **The entity route comes last.** It is tried only after the absolute and the partial route found nothing, so no
   plan-3 binding changes. Its rest is resolved like an absolute path from the carrier, so a numbered polymorphic
   variant is never bound (HEL-23). Reporting stays as in plan 3, once per (condition, message, path).
10. **Type names:** each tag of the path below `message`, capitalised and joined. The root's type is `Message`. A
    shape in which one name would name two paths is refused. There are none among the 5,806 production paths.
11. **One shape for both sides.**
    - The reader expands a published message into `SchemaNode`s, and so does the generator.
    - The writer's output is read back by the same reader, and must give back the shape it was written from.
    - Comparing two shapes is then one pure function.
12. **The like-for-like drift reports are snapshots in the repository** (`test/expected/`). They are derived from
    public files, and a change in what the generator produces shows in review as a change to them.
13. **The fixtures:**
    - The 118 `/api/v1/` files (117 XSDs and `xmldsig-core-schema.xsd`) are pinned per file by a committed manifest,
      and the manifest by one SHA-256 in this plan.
    - The two old workbooks are pinned like the others.
    - The 107 sample messages are not fetched; they are templates (§5.8).

## Review Focus

These are inputs the spec implies but the happy path never exercises. Each has a test in the task that owns the code.

1. **A description or fixed value with `<`, `&`, `"` or `'`.**
   - Expected: the written XSD is well formed, and the text reads back unchanged.
   - → Task 7, "escapes text and attribute values".
2. **An XSD with a DOCTYPE, an external entity included.**
   - Expected: refused with an error naming the file, and nothing fetched.
   - → Task 2, "refuses a DOCTYPE".
3. **Two message files defining a local type under the same name with different content.** e-Dental's
   `dentalTreatment` has three different definitions, in D001, D003 and D006. In all, 19 local type names are
   defined differently in different message files. Expected: each message expands with its own.
   - → Task 2, "keeps each message file's local types to itself".
4. **An entity path with two carriers, and the naming element enclosed by neither.**
   - Expected: unresolved, never the first carrier.
   - → Task 5, "leaves an entity path unresolved when no carrier encloses the naming element".
5. **A message gaining an element.** Expected: no other element's type name changes.
   - → Task 6, "keeps every other type name when an element is added".

**Interfaces:**
- **Produces, typedefs** (exact names and properties):
  - `ValueType { base: string, minLength: number|null, maxLength: number|null, patterns: string[],
    minInclusive: string|null, maxInclusive: string|null, enumeration: string[], totalDigits: number|null,
    fractionDigits: number|null }`.
    - `base` is the built-in's local name: `string`, `int`, `decimal`, `date`, `dateTime`, `boolean`,
      `positiveInteger`, `unsignedInt`, or whatever else a published file uses.
    - `xs:length` reads as equal `minLength` and `maxLength`.
    - Through a chain of restrictions, patterns accumulate and every other facet takes the nearest definition.
  - `SchemaAttribute { name: string, required: boolean, value: ValueType, fixed: string|null,
    documentation: string|null }`.
  - `SchemaNode`:
    - `{ tag: string, path: string, kind: "group"|"field"|"signature", min: number, max: number|null, type: string|null }`;
    - `{ attributes: SchemaAttribute[], children: SchemaNode[], documentation: LocalText|null, origin: SchemaOrigin|null }`.

    `path` is the tag path below `message` (`contents/prescription/lrn`); the root has `""`. A field has
    attributes and no children, and a group the reverse.
  - `SchemaOrigin { file: string, choice: string|null }`. `file` is the file whose type declared the particle.
    `choice` is `"<parent path>#<n>"`, the n-th `xs:choice` of that parent counting from 1, when the particle sits
    inside one.
- **Produces, in `#xsd-reader`:**
  - `parseXsd( text: string, fileName: string ): XsdElement`, where `XsdElement` is
    `{ name: string, attributes: Object<string, string>, children: XsdElement[], text: string }` and `name` is the
    local name, without its prefix;
  - `readXsdSet( files: Array<{name: string, text: string}> ): XsdSet`:
    - `XsdSet { shared: Map<string, {node: XsdElement, file: string}>, messages: Map<string, XsdMessage> }`;
    - `XsdMessage { code: string, file: string, version: string|null, root: XsdElement,
      types: Map<string, {node: XsdElement, file: string}> }`.

    `SHARED_FILES` are the four `NHIS-Commons|Entities|Fields|Nomenclatures.xsd`. A file `NHIS-<code>.xsd` is a
    message. Any other file, xmldsig included, is not indexed.
  - `expandMessage( set: XsdSet, code: string ): SchemaNode`: the root `message`, with `origin` set on every node.
  - `class UnreadableSchemaError extends Error`: thrown as "Cannot read <file>: …" for malformed XML or any DOCTYPE.

**Reading rules**, from the recon reader that measured §5.8:
- A type's content is its base's particles and attributes first, then its own (`xs:extension`).
- An element's inline anonymous `xs:complexType` is read where it stands, and `type` is then `null`.
- A `ref` whose local name is `Signature` is a node of kind `signature`, with tag `Signature`. That covers the
  published `ref="Signature"`, written under a default xmldsig namespace, and the generated `ref="ds:Signature"`.
- The `dataType` attribute is skipped everywhere (§5.5).
- A type with attributes and no particles is a field. Anything else is a group, an empty sequence included.
- A message's own types shadow the shared ones of the same name, and stay within its message.
- `documentation`:
  - An element's comes from its declaration's own `xs:annotation`, by `xml:lang` (`bg` or `en`; none reads as
    `bg`). It is `null` when there is none. The published files annotate types rather than elements, so theirs is
    mostly `null`.
  - An attribute's is the text of its own annotation.
  - Documentation is never compared. It is read for Task 7's round trip.

### Task 3: The blueprint catalogue

**Files:**
- Create:
  - `packages/importer/interpret/blueprint-catalogue.js`;
  - `packages/importer/importer/xsd-importer.js`;
  - test `packages/importer/test/blueprint-catalogue.test.js`, with its public part in `public-xsd.test.js`.

  - `packages/importer/package.json`: imports `#blueprint-catalogue` and `#xsd-importer`, export `./xsd`.

**Interfaces:**
- **Consumes:** `XsdSet`, `expandMessage` (Task 2).
- **Produces:**
  - `Blueprint { key: string, types: string[] }`. `key` is the type its derivation chain starts from in
    `NHIS-Entities`. `types` lists every type that folds into it, the key first, then in file order.
  - `BlueprintCatalogue { blueprints: Blueprint[], published: Object<string, Object<string, string>> }`.
    `published` maps a message code, then a group's tag path, to a blueprint key.
  - `learnCatalogue( set: XsdSet ): BlueprintCatalogue`, deep-frozen.
  - `importXsdSet( directory: string ): Promise<{set: XsdSet, catalogue: BlueprintCatalogue}>`. It reads every
    `*.xsd` in the directory and throws `UnreadableSchemaError` for one it cannot read.

**The rules:**
- **Candidates:** every complex type of `NHIS-Entities.xsd`, and every message-local type whose derivation chain

### Task 6: The message shape

**Files:**
- Create: `packages/spec-model/model/xsd-shape.js`; test `packages/spec-model/test/xsd-shape.test.js`
- Modify: `packages/spec-model/package.json`: export `./xsd-shape`, import `#xsd-shape`

**Interfaces:**
- **Consumes:** `SchemaNode` and friends (Task 2); `CodeList.keyType` (Task 1).
- **Produces:**
  - `CHARSET_PATTERNS`: `{ n: "[0-9]+", an: "[a-zA-Z0-9\\- ]+", a: "[a-zа-яA-ZА-Я\\- ]+" }`, frozen.
  - `typeNameOf( path: string ): string`. `""` gives `"Message"`. Otherwise each `/`-separated tag, with its first
    letter upper-cased, joined.
  - `valueTypeOf( element: ElementNode, codeLists: Map<string, CodeList> ): ValueType`, by the table below.
  - `messageShape( message: Message, codeLists: Map<string, CodeList> ): SchemaNode`.
    - It throws `RangeError` naming both paths when one type name would name two paths, and when two sibling
      elements share a path.

**Value types**, exact (§4.10):

| `dataType` | `base` |
|---|---|
| any, with a code list the map has | `int` if the list is `integer`, else `string` |
| `String`, `Codeable Concept` | `string` |
| `Date and Time` | `dateTime` |
| `Date` | `date` |
| `Boolean` | `boolean` |
| `Decimal` | `decimal` |
| `Positive Int` | `positiveInteger` |
| `Unsigned Int` | `unsignedInt` |
| anything else, or none | `string` |

**Facets:**
- On `string`: `minLength` and `maxLength` from the constraint, and the charset's pattern.
- On the numeric bases: `minInclusive` and `maxInclusive` from `minValue` / `maxValue`, as strings.
- The `yymmdd` format adds the pattern `[0-9]{6}`.
- A code-list value gets no facets beyond its base.

**The shape:**
- The root is `message`, path `""`, type `Message`, `1..1`. Its children are the message's top-level elements in row
  order.
- A group maps to a group node, with its children in row order.
- A root-level group tagged `Signature` maps to a `signature` node.
- A field maps to a field node:
  - its `value` attribute is required, with `fixed` from `fixedValue`;
  - each attribute row under it adds an attribute, required when its requirement is `R`;
  - a coded attribute's `documentation` is `Code list CLxxx.`.
- Polymorphic elements:
  - Its variants are grouped by tag.
  - One tag gives one field node, with the polymorphic element's cardinality. Its value is the variants' type when
    they all have the same one, else `{ base: "string" }` with no facets.
  - Several tags give one field node per tag, each with `min` 0 and its variant's `max`.
- `min` and `max` come from the cardinality. Without one, `min` is 1 for `R` and 0 otherwise, and `max` is 1.
- `documentation` is the element's description when either language has one, else `null`.
- `type` is `typeNameOf( path )`.
- `origin` is `null`.

### Task 9: Synthetic messages, validated by xmllint against both

**Files:**
- Create:
  - `packages/spec-model/model/synthetic-message.js`;
  - tests `packages/spec-model/test/synthetic-message.test.js` and
    `packages/importer/test/xsd-validation.test.js`.
- Modify: `packages/spec-model/package.json`, exporting `./synthetic-message`.

**Interfaces:**
- **Consumes:** `SchemaNode` (Tasks 2, 6); the like-for-like inputs of Task 8.
- **Produces:**
  - `synthesizeMessage( shape: SchemaNode, options?: { omit?: Set<string> } ): string`: a message in the namespace
    `https://www.his.bg`.
    - Every element appears `max( min, 1 )` times, so an optional one appears once. A path in `omit` is left out,
      with everything under it.
    - A signature is written as an empty `<ds:Signature/>` in the xmldsig namespace.
    - Every attribute appears with a value.
  - **Values:**
    - a fixed value when there is one;
    - else, by base: `int` and `positiveInteger` and `unsignedInt` `1`, `decimal` `1.5`, `date` `2026-01-02`,
      `dateTime` `2026-01-02T03:04:05`, `boolean` `true`;
    - else a string. Lengths are tried from `max( minLength, 1 )` up to `maxLength`, or 64 without one. At each
      length, `A`, `1`, `a` and `а` (Cyrillic) are tried, each repeated to that length. The first that matches every
      pattern is used, and `yymmdd`'s `[0-9]{6}` finds `111111`. Patterns are read as JavaScript regular expressions
      anchored at both ends.
    - Numbers respect `minInclusive`.
    - An `enumeration` gives its first value.

An empty `ds:Signature` does not satisfy xmldsig. The validation test therefore checks every error xmllint reports
against `Signature`, and accepts only those. The test lists that rule once, by name, rather than dropping the
element.

**The validation** (`xsd-validation.test.js`), with xmllint-wasm:
- Every non-withdrawn production message's synthetic message is valid against its generated XSD, except for the
  Signature rule.
- For each like-for-like message, the synthetic message is checked against the published XSD.
  - The published XSD's includes are made local: `https://www.his.bg/api/v1/` is removed from each `schemaLocation`,
    and the four shared files and xmldsig are preloaded.
  - `omit` holds the published choices' alternatives: for every `origin.choice` id, every path but the first.
  - The synthetic message is valid, except for errors on paths that have an `unexplained` or `choice` entry in the
    pair's snapshot. Assert exactly that.
